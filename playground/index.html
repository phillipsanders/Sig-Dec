Signed Decisions: the working model

    A small folder of ranked, signed rules that cross components. CRDs cite it, the agent file is generated from it, and a check compares it with the design files on every publish. This page shows each part, using Harbor, a fictional bank, as the example. The same files are in examples/harbor/.

    How to read the labels. example is Harbor: invented for illustration, not a result. tested comes from Experiment 1, or is something the tool in this repository does today. observed comes from an audit of one real project, given as counts only. design intent has not been built or tried with a team. One caution: the experiment’s decisions used the strictness words working, binding and mandatory. The MUST, SHOULD and MAY wording shown here came afterwards and has not yet been tested.

    What counts as a signed decision, and what does not

    The scope is narrow on purpose. A value belongs in a token. A rule about one component belongs in that component’s CRD (Component Requirements Document). The reasoning belongs in the history. A signed decision holds only a rule that several components or flows must follow, with the four things nothing else carries: a scope across components, a rank, a signer and a review date.

    How it starts: sort what exists

    Nobody writes decisions from a blank page. A team that works with agents already has an agent file, and usually some record of past decisions. Starting is three sorting jobs.

    1. Sort the existing decision records. Keep the ones that are still live and that cross components. The rest stay where they are, as history.
    2. Split the agent file. Each section stays, becomes a decision, or is deleted because it should be read live. The panel below shows the split.
    3. Ask each function to sign, reword or reject. Nothing is delivered to an agent until then.

    An agent file, section by section

    Where the decisions and the justifications live

    Decisions get their own folder at the top of the repository that holds the CRDs. They sit beside the records, not inside them, because a decision crosses components. They sit outside the agent file, because the agent file is an output. The justification is not copied: each decision links to the history entry that explains it.

    Review, and how a decision becomes a token, a CRD statement or a lint rule
    
  
    A decision is meant to leave the folder. Once a rule is built into the system, nobody needs to read it any more: the token, the CRD or the build enforces it. Review is where that is decided.
    
  
    Every decision comes up for review on a date: a MUST each year, a SHOULD after twelve months, a MAY after ninety days. Four events bring it forward: its check fails, a designer’s call is logged against it, another decision overrides it, or it still owes a justification. The signers, by function, choose one of four outcomes: renew, reword, retire or promote.

    What it does not do
    
    
      
      
    • It does not replace the CRD. About a third of the 34 deviations sat inside one component, and the CRD is the better tool for those.
      • 
      
    • It does not write the checks. Each decision needs one, written by hand.
      • 
      
    • It does not decide. Where two records disagree it names the functions that must settle it.
      • 
      
    • It is not proven with people. Nothing yet shows that anyone will write or sign. Decision records have failed this way before: about half the projects that adopted them wrote fewer than five (Buchgeher et al., 2023).
      • 
      
    • One experiment. One model, one flow, five runs per condition, no human raters. Token savings and steadier runs were predicted and did not hold.
      •
